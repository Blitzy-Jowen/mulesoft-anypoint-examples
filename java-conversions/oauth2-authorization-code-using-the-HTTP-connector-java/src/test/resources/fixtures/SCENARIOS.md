# Parity scenarios — oauth2-authorization-code-using-the-HTTP-connector-java

Scenarios for the fixture replay (ST-2) of `oauth2-authorization-code-using-the-HTTP-connector-java`. The original example is `oauth2-authorization-code-using-the-HTTP-connector` (folder `oauth2-authorization-code-using-the-HTTP-connector/`), whose only configuration file is `src/main/app/http-authorization-code-web.xml`, the single entry of `config.resources` in its `mule-deploy.properties`. On the HTTP listener `localhost:8081`, flow `boxUserLoginFlow` answers `/web` with a redirect to the local authorization URL, and flow `userLoginDoneFlow` answers `/web/loginDone` by searching Box with the stored access token. From the `oauth2:authorization-code-grant-type` of the Box request configuration the Mule 3.8 platform opens an HTTPS listener on `localhost:8082` with two generated handlers (AAP 0.4.5): `/authorization` sends the browser to the Box authorization URL, and `/redirectUrl` exchanges the authorization code at the Box token URL and stores the tokens in `Token_Manager_Config`. Every branch of the two flows and the two handlers, and the listener-boundary cases of AAP 0.4.7, is exactly one scenario below, and each captured scenario's fixture is `fixtures/<scenario>.json`.

This file follows the reference format kept in `java-conversions/hello-world-java/src/test/resources/fixtures/SCENARIOS.md`: its headings, table header, cell notation and prose sections are copied from there, and its rows come from AAP 0.7.5 and the platform surfaces of AAP 0.4.5. Its consumer is `src/test/java/com/mulesoft/examples/oauth2_authorization_code_using_the_http_connector/FixtureParityTest.java`, the project's copy of ST-2, which reads this file from the classpath as `fixtures/SCENARIOS.md`, or as `<dir>/SCENARIOS.md` under `-Dfixtures.dir=<dir>`. Until Tier 2A capture writes fixtures, this file is the only one in `src/test/resources/fixtures/`; no fixture is ever written by hand. The project `README.md` lists these scenario names and the unverified ones.

Request notes:

- Each `Request` cell starts with the listener it targets, in the prefix form of the multi-listener project `http-oauth-provider-java`: HTTP `localhost:8081`, the main listener, or HTTPS `localhost:8082` with client certificate, the SC-10 listener `box-oauth` (Ports below). `FixtureParityTest` validates only the `Scenario`, `Trigger` and `State` cells of a row; the replay takes the listener from the fixture's `request.port` and `request.portProperty`, and TLS from `request.tls`.
- Queries are sent byte for byte as written. The `state` parameter of `get-redirect-url-success-with-state`, `get-redirect-url-no-code-with-state`, `get-redirect-url-token-call-failed-with-state` and `get-redirect-url-token-not-found-with-state` is the percent-encoded state the platform's local-authorization handler builds for `onCompleteRedirectTo=http://localhost:8081/web/loginDone` with no original state (Mule 3.8 `StateEncoder`), written in full in each row. In `get-authorization-with-on-complete-redirect` the `onCompleteRedirectTo` value is sent unencoded, as written.
- `code=test-code` is a fixed code that no Box server granted; the token exchanges it triggers are answered by capture stubs (note 3).
- The `Request` cells name only the headers the capture sets explicitly. The headers curl adds by default are recorded unedited in each fixture's `request.headers` from curl's trace (Capture step 5).

Ports:

- The main listener is `HTTP_Listener_Configuration`, `localhost:8081` (`http-authorization-code-web.xml:26`): key `server.port` (default `8081`, bound to `server.address` `localhost`), serving `/web` and `/web/loginDone` (`listeners.main.routes` in `src/main/resources/application.yml`).
- The SC-10 HTTPS listener `box-oauth` (`listeners.additional[0]`) is `localhost:8082`, the port of `localAuthorizationUrl` and `redirectionUrl` (`http-authorization-code-web.xml:6-7`): key `ports.box-oauth` (default `8082`), serving `/authorization` and `/redirectUrl`. It runs over `TLS_Context` (`http-authorization-code-web.xml:21-24`), key store `keystore.jks` and trust store `trust-store`, both carried in `src/main/resources/`. Because `TLS_Context` carries a trust store, the listener requires a client certificate that the trust store accepts, as the Mule 3.8 listener did (`config/ListenerPorts`).
- SC-10 `PortRoutingFilter` answers a path requested on the listener that does not serve it (`get-authorization-on-http-port`, `get-web-on-https-port`).
- The original hard-codes both ports, so the capture runs on `8081` and `8082`: `request.port` is `8081` in every HTTP row and `8082` in every HTTPS row. An HTTPS fixture names `ports.box-oauth` in `request.portProperty`; an HTTP fixture leaves it at its default `local.server.port`.

Notes for this project:

1. **HTTPS rows** (`get-authorization-with-on-complete-redirect`, `get-authorization-without-on-complete-redirect`, the six `get-redirect-url-*` rows and `get-web-on-https-port`). They replay through ST-1 `support/HttpTestClient` in its TLS client-certificate mode when the copied ST-2 driver provides it. That mode is ST-1's `HttpTestClient.https(host, port, trustStorePath, trustStoreType, trustStorePassword, keyStorePath, keyStoreType, keyStorePassword)`, which this project's ST-1 copy carries, opened with the carried `src/main/resources/trust-store` and `src/main/resources/keystore.jks` (type `JKS`, password `mule123` for both stores and the key, the demo value `src/test/resources/application-test.yml` supplies) against the SC-10 listener `box-oauth`. The copied ST-2 driver does not provide it: its `request.tls` object (`trustStore`, `type`, `password`) opens only ST-1's trust-store overload `HttpTestClient.https(host, port, trustStorePath, trustStoreType, trustStorePassword)`, which presents no client certificate, so `box-oauth` refuses the handshake and a fixture would be reported `FAILED` against a correct conversion. The replay therefore has no driver for these rows, which the README reports as unverified for the missing client-certificate driver (the condition `UNVERIFIED-missing-driver` names). Their capture output is committed as evidence in `src/test/capture/<scenario>/` without a `fixtures/<scenario>.json`, so `FixtureParityTest` lists them `UNVERIFIED-uncaptured` and never `FAILED` or `VERIFIED`. When ST-2 passes a client key store to ST-1, their fixtures are written from that evidence (Capture step 8), with `request.portProperty` `ports.box-oauth` and `request.tls` naming both carried stores.
2. **Token store.** `get-login-done-no-token`, `get-login-done-authorized`, `get-redirect-url-success-with-state` and `get-redirect-url-success-without-state` depend on the state of `Token_Manager_Config`, which the conversion keeps in memory in `service/BoxOAuthService`: `get-login-done-no-token` needs an empty store, `get-login-done-authorized` a stored token, and the two success rows store one. The `state` contract has no member that seeds or empties this store (`state.clearCaches` empties only `CacheManager` caches), so each row's seeded state is established by order, the same way at capture and at replay, whatever order the fixture files are found in: the capture sends every row except `get-login-done-authorized` in table order to one fresh deployment (Capture step 3), and the replay runs the rows in table order in one fresh application context. No row before `get-login-done-no-token` stores a token, so it meets an empty store at both, and no row after the two success rows reads the store, because only `/web/loginDone` does. `get-login-done-authorized` needs a token from an interactive Box login, which neither `state` nor prior requests can reproduce. It is captured in its own deployment against the real Box (Capture step 2), and its only outbound call, the Box search, carries the access token Box issued, a live value, so its fixture omits `upstream` (Capture step 2 of the reference) and `FixtureParityTest` reports it `UNVERIFIED-no-upstream` instead of replaying it against an empty store. Table rules, for every project that copies this format:

- The header is exactly the seven columns above, with these names and in this order, followed by a separator row of `-` cells. `FixtureParityTest` fails the class on any other header, a missing separator row or an empty table.
- Cells are split on unescaped `|`, so a `|` inside a cell is written `\|`. Each cell is trimmed and unescaped, and its surrounding backticks are stripped, so code spans are allowed. The table ends at the first line that does not start with `|`.
- `Scenario` is kebab-case (`[a-z0-9]+(-[a-z0-9]+)*`), unique in the file, formed from the entry point and the branch (AAP 0.8.4), and equal to the fixture file name without `.json`.
- `Trigger` is one of `http`, `soap`, `file`, `jms`, `amqp`, `mq`, `mail`, `scheduler`. It selects the replay driver.
- `State` is one of `deterministic`, `nondeterministic`, `unreachable`. A `nondeterministic` row names in `Branch` what varies (the current time, random values, a generated name). An `unreachable` row states in `Branch` the proof that no input selects it (AAP 0.8.2).
- `Request` is the exact input the capture sends, written as: `METHOD /path` (with `?query` when there is one); then each request header as header `Name: value`, in sending order; then the body as `empty body`, as an inline code span written byte for byte (body `hello`), or as body = the bytes of `<file>` (`src/test/resources`) for a file body, which is never inlined. Non-HTTP rows name the input file, message or mail, and the single-run method the replay invokes. In this project the listener prefix of Request notes comes first.
- `Seeded state` is `none`, or a short description of what the fixture's `state` seeds (rows, files, messages, mailboxes, a watermark) or, in this project, of the token-store state and the upstream recording a row depends on.
- `Branch` names the flow path the request selects. Outcome words written there name the branch. They are never captured values; the captured fixture alone holds the response.
- `Source` cites the original by file and line; a platform-generated surface cites the element it is generated from.
- Every row of this file is captured by sending its request to the unmodified original on its fixed ports `8081` and `8082` (see Capture).

## Fixture contract

Fixtures are `fixtures/<scenario>.json` beside this file (`src/test/resources/fixtures/`), loaded from the classpath as `classpath*:fixtures/*.json`. With `-Dfixtures.dir=<dir>` set, the test reads `<dir>/SCENARIOS.md` when it exists and loads only `<dir>/*.json`; this override is for local engine checks. There is one fixture per row, and a fixture without a matching row fails the class. Each fixture is one JSON object with the four top-level sections of AAP 0.8.4: `request` and `response` are required, `state` and `upstream` are read when present, and any other top-level key is ignored. Every value is written unedited from the capture.

`request`, for `http`, the trigger of every row of this project:

- `method`: the request method as sent.
- `path`: the request path, without the query.
- `query`: the raw query string without `?`, appended as `?<query>` when non-empty; `""` when there is none.
- `headers`: an ordered array of `[name, value]` pairs, in the order they were sent. `Host` is recorded as sent. Only transport fields are regenerated: the replay drops the recorded `Host`, `Content-Length`, `Connection` and `Transfer-Encoding` and writes its own `Host` for the replay port, and ST-1 writes `Content-Length` for the body and `Connection: close`. Every other recorded pair is sent as its own header line, in recorded order, through ST-1's `HttpTestClient.sendHeaderPairs`; a repeated name, such as two `Cookie` pairs, stays on separate lines and is never joined.
- `body` (UTF-8 text) or `bodyBase64` (binary); an empty body is `""` or omitted.
- `port`: the listener port the capture targeted (`8081` for an HTTP row and `8082` for an HTTPS row in this project, as the row's `Request` names it). It is the port replaced inside `Location` on replay.
- `portProperty`: optional; the Spring property that holds the replay port of the targeted listener, default `local.server.port`. Multi-port projects (SC-10) name the extra listener's port key here; in this project an HTTPS row names `ports.box-oauth`.
- `tls`: optional object `{trustStore, type, password}` for HTTPS listeners, replayed through ST-1's TLS mode. `trustStore` resolves from the classpath first, then as a file. It configures no client certificate, which is why the HTTPS rows of this project have no fixture yet (note 1).
- `readTimeoutMillis`: optional; the replay's socket read budget for this request, a positive whole number of milliseconds, applied through ST-1's `HttpTestClient.withReadTimeout` to every read of the reply, the TLS handshake's included; default 10000, ST-1's `TIMEOUT_MILLIS`, which also stays the connect timeout. Like `awaitMillis`, it is a replay setting, not a captured value: a fixture sets it when the endpoint itself waits about 10000 ms or longer before it answers, so that the replay reads the captured answer instead of timing out before the comparison.

The `request` members of the other drivers (`file`, `invoke`, `awaitMillis`, `message`, `mail`) are defined in the reference and apply to no row of this project.

`state`, seeded before the run:

- `properties`: Spring property overrides `{key: value}`, registered before the application context starts. Values may use the placeholders below. The same key resolving to different values in two fixtures fails the class.
- `notContacted`: an array of property keys, each a non-blank string, that the original never connected to, such as an OAuth authorization URL it only returned in a redirect, or a CORS origin. The replay boundary below does not check them; the keys of every fixture together apply to the one application context.
- `clearCaches`: optional, `true` or `false`, the default. `true` stands for the restart the capture made before the scenario, after which the original's in-memory stores were empty: once the `state` is seeded, and before the prior requests and the input, the replay empties every cache of every `org.springframework.cache.CacheManager` bean of the application context. A project without such a bean reports the scenario `UNVERIFIED-missing-driver`, since the replay cannot re-create the empty stores the capture started from. Without `clearCaches`, the application's caches and its other in-memory state carry over from the scenarios before, in table order.
- `requests`: optional; the prior requests the capture sent before the scenario's own, in the order sent, each an object of the `request` shape above (`method`, `path`, `query`, `headers`, `body` or `bodyBase64`, `portProperty`, `tls`, `readTimeoutMillis`). The replay sends them through ST-1 after the `state` is seeded, its caches cleared and the `upstream` stubs installed, and before the input. Their replies are discarded, as the capture discarded them, whatever their status; one that cannot be sent, or whose reply cannot be read, fails the scenario. Their outbound calls are recorded in `upstream`, in call order.
- The other members of the reference's `state` (`directories`, `tables`, `collections`, `ldap`, `amqp`, `jms`, `mail`) seed stores this original never reaches.
- For this project, `state` holds only `properties` and `notContacted`, the same in every fixture (Replay state, in the notes under Scenarios).

`upstream`, the recorded outbound calls:

- An ordered array of `{request, response}` pairs, one per outbound call the original made, in call order. `request` holds `method`, `url`, `headers` and `body` or `bodyBase64`; `response` holds `status`, `headers` and `body` or `bodyBase64`. Headers are either `[[name, value]]` pairs or a `{name: value}` object. Each pair is converted from the request journal of the capture's WireMock (Capture steps 2 and 7): `url` is the path and query relative to the WireMock base, so no live host is named, and bodies are the entity bytes exchanged, de-chunked, with a response `Content-Encoding` left encoded.
- On replay WireMock serves the recording in order. Every recorded call must be made, in order, with the same method, URL, body and headers, and no other call may be made. `Host`, `Content-Length`, `Connection` and `Transfer-Encoding` are ignored; `User-Agent` and `Accept-Encoding` are compared only when the inbound `request.headers` carried the same header with the same value.
- `"upstream": []` means the scenario was recorded and made no outbound calls: the empty array is a complete recording, not a missing one. In this project the four token-exchange rows (`get-redirect-url-success-with-state`, `get-redirect-url-token-call-failed-with-state`, `get-redirect-url-token-not-found-with-state`, `get-redirect-url-success-without-state`) record their stubbed token exchange, and every other captured row records what its journal holds.
- A missing `upstream` key means the recording is incomplete: the scenario is skipped and reported `UNVERIFIED-no-upstream`. Capture leaves it out where an exchange cannot be recorded locally or without live values (steps 2, 7 and 8), as for `get-login-done-authorized`.

`response`, the captured result:

- `status` and `reason`: the status code, as a JSON number, and the reason phrase of the final raw status line.
- `headers`: `{Content-Type, Location}`, each only when the original sent it, with its value as received. An absent or null value means the Java response must not send that header. Other headers are not recorded.
- `body` (UTF-8 text) or `bodyBase64` (binary): the entity bytes with only the transport framing removed (chunked coding de-chunked, a `Content-Length` body taken exactly) and any `Content-Encoding` left encoded, extracted from the raw capture as Capture step 6 defines.
- The non-HTTP effects and the `logs` of the reference's `response` are not recorded for this project: its original writes no file, message, row, document or mail, and Capture step 6 records the HTTP result only.

Placeholders, allowed in `state.properties` values and resolved at replay; this project uses the first two:

- `${wiremock.baseUrl}` (`http://localhost:<port>` of the WireMock server that serves `upstream`) and `${wiremock.port}`.
- `${freePort:<name>}`: a free port, the same one for every use of the same name.
- `${dir:<name>}`, `${greenmail.<proto>.port}`, `${mongo.uri}` and `${ldap.port}`, defined in the reference.

Any other placeholder fails the class with a message naming the placeholder and the fixture.

Replay boundary, applied to the application context before any of its beans exists, so replay never contacts a live service:

- Scheduling is suppressed: Spring's `@Scheduled` processor is removed, so no `@Scheduled` method or `SchedulingConfigurer` task runs by itself; this project schedules nothing.
- Every key of the context's property sources, except the host's environment variables and system properties, is checked with its effective value, together with the Spring Boot connection keys the reference names. A target the replay owns is a loopback host (`localhost`, any IPv4 loopback address, `::1`, `0.0.0.0`) on the WireMock port, a `${freePort:<name>}` port or an embedded server's port, or an in-JVM address (`vm:`, `file:`, `classpath:`, `jar:`). The checks cover every `scheme://host[:port]` in a value, with the scheme's default port when none is given, and a key whose last segment ends with `host` or is `hostname`, read with its sibling `port`; the reference lists the JDBC, `host(port)` and client-default forms, which this project does not configure. Only port `0` on a loopback host, the application's own random listener, is skipped.
- Any other target fails the class before the application context starts, with a message naming each key, its value, the target's `host:port` and the remedy: override the key through `state.properties` with a replay-owned value (`${wiremock.baseUrl}`, `${freePort:<name>}`), or list it in `state.notContacted`. For this project that is the Replay state in the notes under Scenarios: the Box upstream keys are overridden, and the redirect URLs and the HTTPS bind host are listed as not contacted.
- WireMock runs whenever a fixture is loaded, so an outbound HTTP call the recording lacks fails its scenario, `"upstream": []` included.
- Diagnostics mask credentials: a value whose key's last segment names a secret (a word such as `password`, `secret`, `token`, `key` or `auth`) is shown as `***`; otherwise URI user information (`scheme://***@host`) and parameters with such names (`password=***`) are masked. Keys, hosts and ports stay readable.
- Each scenario starts from a reset (WireMock and the captured log events) and gets its `upstream` stubs before its `state` and input are written. The reset clears no application cache and no other in-memory state of the application, the token store of `service/BoxOAuthService` included, so scenarios that build on one another in table order keep doing so (note 2).

## Comparison rules

- `deterministic`: status, reason, `Content-Type`, `Location` and body bytes are compared byte for byte, with no trimming or normalization. The only substitution is the replay port inside `Location` (`:<request.port>` becomes `:<replay port>`).
- `nondeterministic`: status, reason and the checked headers are compared exactly. Bodies are compared for structure only: JSON by each object's member names in order, every occurrence of a repeated name kept, value kinds and array lengths; XML by child element names (namespace and local name) in order and attribute names as a set, with namespace declarations excluded and text ignored; any other body by empty versus non-empty. Upstream request bodies are not matched. The scenario is reported `UNVERIFIED — nondeterministic output`.
- `unreachable`: no fixture may exist; the proof belongs in the row (AAP 0.8.2). A fixture for an unreachable row fails the class, and the scenario is `FAILED`. This project has no such row.

Each run writes `target/fixture-parity/summary.properties` in the project directory: first the counts `verified=<n>`, `unverified=<n>` and `failed=<n>`, then one `scenario.<name>=<STATUS>` line per row, in row order. The statuses:

- `VERIFIED`: a captured deterministic fixture matched.
- `UNVERIFIED-nondeterministic`: a nondeterministic fixture matched in structure only.
- `UNVERIFIED-no-upstream`: the fixture has no `upstream` key.
- `UNVERIFIED-missing-driver`: the project has no replay driver (library, bean or port) for the row's trigger.
- `UNVERIFIED-uncaptured`: the row has no fixture file.
- `UNREACHABLE`: an unreachable row with no fixture.
- `FAILED`: a mismatch, a fixture for an unreachable row, or a fixture with no matching row.

`VERIFIED` counts as verified, every `UNVERIFIED-*` status as unverified and `FAILED` as failed; `UNREACHABLE` is counted in none.

With no fixtures the test is reported skipped (`Assumptions.assumeTrue`, reason `no Tier 2A fixtures captured`), never failed. For this project the summary then lists all fifteen scenarios as `UNVERIFIED-uncaptured`, with `verified=0`, `unverified=15` and `failed=0`. After capture the nine HTTPS rows keep that status until ST-2 provides a client-certificate mode (note 1), and `get-login-done-authorized` is `UNVERIFIED-no-upstream` (note 2). These statuses feed the parity labels of note 4.

   - `headers`: the `Content-Type` and `Location` values as received.

Under a `Transfer-Encoding` whose last coding is `chunked`, they are the chunk data concatenated, without the chunk-size lines, chunk extensions, CRLFs, last chunk or trailer fields; under `Content-Length`, exactly that many bytes; under neither, every byte to the end of the output; none for a `HEAD` request or a status that carries no body by HTTP/1.1.
