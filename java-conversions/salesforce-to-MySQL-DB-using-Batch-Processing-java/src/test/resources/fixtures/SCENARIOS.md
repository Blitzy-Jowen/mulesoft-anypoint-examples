# Parity scenarios — salesforce-to-MySQL-DB-using-Batch-Processing-java

Scenarios for the fixture replay (ST-2) of `salesforce-to-MySQL-DB-using-Batch-Processing-java` (package `com.mulesoft.examples.salesforce_to_mysql_db_using_batch_processing`). The original example is `salesforce-to-MySQL-DB-using-Batch-Processing` (folder `salesforce-to-MySQL-DB-using-Batch-Processing/`), a third-party connector example that is poll-triggered and has no HTTP listener (`spring.main.web-application-type: none`). Its flow `triggerFlow`, in the only flow file `config.resources=salesforce-to-database.xml` selects, polls every 60 s: it resolves the watermark `timestamp` (the stored value, or while none is stored the `default-expression`, the current time minus 10 s formatted `yyyy-MM-dd'T'HH:mm:ss.SSS'Z'` in UTC), queries Salesforce through `sfdc:query` for the Contacts modified after it, logs the watermark, and hands the records to the batch job `salesforce-to-database-Batch`. Its step `queryExistingContactInDbStep` maps each Contact to the `contact` columns and looks the email up in the MySQL database `company`; its step `upsertContactInDbStep` inserts the row when the lookup found none and updates it when it found one; `batch:on-complete` logs `Batch sf->db has finished`; and the watermark moves to the MAX `LastModifiedDate` the query returned. The branches AAP 0.7.4 lists for the example (the default and the stored watermark, the insert and the update branch), the poll behaviour SC-7 and SC-8 (AAP 0.4.4) define for an empty query and a failing record, the poll whose Salesforce connection is refused, and the one branch no input selects (AAP 0.8.2) are one scenario each below, and each reachable scenario's captured fixture is `fixtures/<scenario>.json`.

No fixture JSON exists yet: fixtures are written only by the Tier 2A capture against the running original (see Capture), and the ones this file would receive are `fixtures/scheduler-poll-default-watermark.json`, `fixtures/scheduler-poll-new-contact-inserted.json`, `fixtures/scheduler-poll-existing-contact-updated.json`, `fixtures/scheduler-poll-no-records.json`, `fixtures/scheduler-poll-record-failure.json` and `fixtures/scheduler-poll-upstream-unavailable.json`. `scheduler-poll-otherwise-branch` is `unreachable` and never gets one. Until capture, `mvn -B test` reports `FixtureParityTest` skipped, and the project carries `PARITY: UNVERIFIED — Mule runtime unavailable`.

This file follows the reference format kept in `java-conversions/hello-world-java/src/test/resources/fixtures/SCENARIOS.md`: its headings, table header, cell notation and prose sections are copied from there and adapted to this project's scheduler trigger, as `java-conversions/salesforce-data-synchronization-using-watermarking-and-batch-processing-java/src/test/resources/fixtures/SCENARIOS.md` adapts them for the same poll, watermark and Salesforce upstream and `java-conversions/querying-a-mysql-database-java/src/test/resources/fixtures/SCENARIOS.md` for a MySQL database replayed on H2; its rows come from AAP 0.7.4.

## Fixture contract

Fixtures are `fixtures/<scenario>.json` beside this file (`src/test/resources/fixtures/`), loaded from the classpath as `classpath*:fixtures/*.json`. With `-Dfixtures.dir=<dir>` set, the test reads `<dir>/SCENARIOS.md` when it exists and loads only `<dir>/*.json`; this override is for local engine checks. There is one fixture per row, and a fixture without a matching row fails the class. Each fixture is one JSON object with the four top-level sections of AAP 0.8.4: `request` and `response` are required, `state` and `upstream` are read when present, and any other top-level key is ignored. Every value is written unedited from the capture.

`request`, for `http` and `soap`:

- `method`: the request method as sent.
- `path`: the request path, without the query.
- `query`: the raw query string without `?`, appended as `?<query>` when non-empty; `""` when there is none.
- `headers`: an ordered array of `[name, value]` pairs, in the order they were sent. `Host` is recorded as sent. Only transport fields are regenerated: the replay drops the recorded `Host`, `Content-Length`, `Connection` and `Transfer-Encoding` and writes its own `Host` for the replay port, and ST-1 writes `Content-Length` for the body and `Connection: close`. Every other recorded pair is sent as its own header line, in recorded order, through ST-1's `HttpTestClient.sendHeaderPairs`; a repeated name, such as two `Cookie` pairs, stays on separate lines and is never joined.
- `body` (UTF-8 text) or `bodyBase64` (binary); an empty body is `""` or omitted.
- `port`: the listener port the capture targeted. It is the port replaced inside `Location` on replay. This project has no HTTP listener, so its fixtures carry no `port`.
- `portProperty`: optional; the Spring property that holds the replay port of the targeted listener, default `local.server.port`. Multi-port projects (SC-10) name the extra listener's port key here.
- `tls`: optional object `{trustStore, type, password, keyStore, keyStoreType, keyStorePassword}` for HTTPS listeners, replayed through ST-1's TLS mode; each member is a string, and only `trustStore` is required. `type` is the store type (default `JKS`) and `password` the trust store's password. `keyStore` is a client key store, for a listener that requires a client certificate: with it the replay sends through ST-1's key-store overload `HttpTestClient.https(host, port, trustStorePath, trustStoreType, trustStorePassword, keyStorePath, keyStoreType, keyStorePassword)`, which presents the store's client key; `keyStoreType` defaults to `type`, and `keyStorePassword` is the password of the key store and of its key entries. Without `keyStore` no client certificate is presented. `keyStoreType` or `keyStorePassword` without `keyStore` fails the scenario, and a project whose ST-1 lacks the key-store overload reports a scenario with `keyStore` `UNVERIFIED-missing-driver`. `trustStore` and `keyStore` resolve from the classpath first, then as a file.
- `readTimeoutMillis`: optional; the replay's socket read budget for this request, a positive whole number of milliseconds, applied through ST-1's `HttpTestClient.withReadTimeout` to every read of the reply, the TLS handshake's included; default 10000, ST-1's `TIMEOUT_MILLIS`, which also stays the connect timeout. Like `awaitMillis`, it is a replay setting, not a captured value: a fixture sets it when the endpoint itself waits about 10000 ms or longer before it answers, so that the replay reads the captured answer instead of timing out before the comparison.

`request`, for the other drivers:

- `file`: `{directory, name, body}` or `{directory, name, bodyBase64}`; the input file placed in the trigger's input directory before the run.
- `invoke`: `{bean, method}` or `{type, method}`; the single-run method the replay calls. `bean` is a bean name; `type` is a class name, fully qualified or relative to the test package (for example `{"type": "trigger.OrderFileTrigger", "method": "pollOnce"}`). It is required for the `file`, `scheduler` and `mail` triggers: scheduled triggers do not run during replay (see the replay boundary below), so such a fixture without `invoke` fails its scenario.
- `awaitMillis`: how long the replay waits for asynchronous effects; default 10000.
- `message`: for `jms` and `mq`, `{destination, pubSub, body or bodyBase64, properties}`; for `amqp`, `{exchange, routingKey, body or bodyBase64, properties}`. `body` is sent as a text message and `bodyBase64` as bytes.
- `mail`: `{user, mimeBase64}`; the raw MIME message to deliver, Base64-encoded, and the email address of the receiving mailbox.

`state`, seeded before the run:

- `properties`: Spring property overrides `{key: value}`, registered before the application context starts. Values may use the placeholders below. The same key resolving to different values in two fixtures fails the class.
- `notContacted`: an array of property keys, each a non-blank string, that the original never connected to, such as an OAuth authorization URL it only returned in a redirect, or a CORS origin. The replay boundary below does not check them; the keys of every fixture together apply to the one application context.
- `directories`: `{<directory>: [{name, body or bodyBase64}]}`, the files seeded per named directory. A scheduler watermark is seeded here as the SC-8 store file.
- `tables`: `{<table>: [{<column>: <value>}]}`, the rows inserted after the table is emptied. Table and column names match `[A-Za-z0-9_]+`. Each table must already exist, created when the application starts or by an earlier scenario in table order: the replay creates no table, so a seeded table that does not exist fails the scenario before any row is written.
- `collections`: `{<collection>: [<document>]}`, MongoDB documents as Extended JSON.
- `ldap`: `{baseDn, bindDn, bindPassword, ldif}`, where `ldif` is a classpath resource or inline LDIF text.
- `amqp`: `{initialConfigurationResource, responders}`. `initialConfigurationResource` is the classpath Qpid Broker-J configuration that declares the broker objects and messages. `responders`, present when the capture ran a responder, is `[{queue, reply: {body or bodyBase64, properties}}]`, one entry per responder: it took one request off `queue` and published `reply`, with `properties` as its application headers and the request's correlation id, to the request's reply-to address. The replay starts each responder through the project's `RabbitTemplate` after the drain and before the input is sent, and joins it before comparing the effects; no request on `queue` within `awaitMillis`, a request without a reply-to address or a reply that cannot be sent fails the scenario.
- `jms`: `{denySend: [{destination, pubSub}]}`, the destinations whose producer sends the capture's broker refused; `pubSub` is `true` for a topic and `false`, the default, for a queue. From before the input is sent until the reset, the application's embedded Artemis server refuses every send to them, the application's own included, as Artemis refuses a send its security settings deny: the send fails with a security exception, and a transacted session's transaction is marked rollback-only, so its commit fails. A project whose JMS connection factory does not reach an embedded Artemis server in-VM reports the scenario `UNVERIFIED-missing-driver`.
- `mail`: `{users: [{email, login, password}]}`, the mailboxes.
- `clearCaches`: optional, `true` or `false`, the default. `true` stands for the restart the capture made before the scenario, after which the original's in-memory stores were empty: once the `state` is seeded, and before the prior requests and the input, the replay empties every cache of every `org.springframework.cache.CacheManager` bean of the application context. A project without such a bean reports the scenario `UNVERIFIED-missing-driver`, since the replay cannot re-create the empty stores the capture started from. Without `clearCaches`, the application's caches and its other in-memory state carry over from the scenarios before, in table order.
- `requests`: optional; the prior requests the capture sent before the scenario's own (Capture step 4 of the reference format), in the order sent, each an object of the `request` shape for `http` and `soap` above (`method`, `path`, `query`, `headers`, `body` or `bodyBase64`, `portProperty`, `tls`, `readTimeoutMillis`). The replay sends them through ST-1 after the `state` is seeded, its caches cleared and the `upstream` stubs installed, and before the input. Their replies are discarded, as the capture discarded them, whatever their status; one that cannot be sent, or whose reply cannot be read, fails the scenario. Everything else they cause belongs to the scenario: their outbound calls are recorded in `upstream`, in call order, and the effects read back after the run (files, messages, rows, documents, mails) include theirs. Only their log events are left out: the replay drops the events logged before the input, as `response.logs` holds the events from the input on.
- For this project, `state` holds `properties`, the replay context of Project notes, the same in every fixture (Capture step 7); `tables` with `contact`, the rows Capture step 3 seeded into the original's database, or `[]` where it seeded none, so the replay always empties the table first; and `directories` with the SC-8 store directory `watermark`: `{"watermark": [{"name": "watermark.properties", "body": "timestamp=<seeded value>\n"}]}`, whose one line carries the value Capture step 3 seeded into the original's object store, or `{"watermark": []}` for `scheduler-poll-default-watermark`, which seeds none. The Salesforce sandbox state a row names (the test Contact modified after its watermark) and the refused connection of `scheduler-poll-upstream-unavailable` are conditions of the capture (Capture step 3), not part of `state`, since the replay reaches no live Salesforce.

`upstream`, the recorded outbound calls:

- An ordered array of `{request, response}` pairs, one per outbound call the original made, in call order. `request` holds `method`, `url`, `headers` and `body` or `bodyBase64`; `response` holds `status`, `headers` and `body` or `bodyBase64`. Headers are either `[[name, value]]` pairs or a `{name: value}` object. Each pair is converted from the request journal of the WireMock recording proxy (Capture steps 2 and 5): `url` is the path and query relative to the WireMock base, so no live host is named, and bodies are the entity bytes exchanged, de-chunked, with a response `Content-Encoding` left encoded.
- On replay WireMock serves the recording in order. Every recorded call must be made, in order, with the same method, URL, body and headers, and no other call may be made. `Host`, `Content-Length`, `Connection` and `Transfer-Encoding` are ignored; `User-Agent` and `Accept-Encoding` are compared only when the inbound `request.headers` carried the same header with the same value.
- `"upstream": []` means the scenario was recorded and made no outbound calls. No scenario of this project records `[]`: every poll that reaches Salesforce logs in and queries it, and the connection attempt `scheduler-poll-upstream-unavailable` makes is one the replay cannot reproduce at the shared `sfdc.auth-endpoint`, so `[]` would misstate it (Project notes, Upstream unavailable).
- A missing `upstream` key means the recording is incomplete: the scenario is skipped and reported `UNVERIFIED-no-upstream`. Capture leaves it out where an exchange cannot be recorded locally or without live values (steps 2, 5 and 7); all six reachable scenarios of this project omit it (Project notes, `serverUrl` routing and Upstream unavailable).

`response`, the captured result:

- `status` and `reason`: the status code, as a JSON number, and the reason phrase of the final raw status line.
- `headers`: `{Content-Type, Location}`, each only when the original sent it, with its value as received. An absent or null value means the Java response must not send that header. Other headers are not recorded.
- `body` (UTF-8 text) or `bodyBase64` (binary): the entity bytes with only the transport framing removed (chunked coding de-chunked, a `Content-Length` body taken exactly) and any `Content-Encoding` left encoded, extracted from the raw capture as Capture step 6 of the reference format defines. This project's fixtures record no HTTP response.
- Non-HTTP effects:
  - `directories`: the exact final file set of each named directory, so a consumed input directory is `[]` (SC-5 disposition).
  - `messages`: `[{destination, pubSub, body or bodyBase64, properties}]`, the messages the capture found on the destinations of `destinations`, each destination's in the order the capture received or browsed them; on an AMQP broker, `destination` is the queue. Bodies and the listed properties are compared, and every destination of `destinations` must hold exactly its entries, so one without entries must stay empty.
  - `destinations`: `[{destination, pubSub}]`, every destination the capture subscribed to or browsed, in capture order, those it found empty included; `pubSub` is `true` for a topic and `false`, the default, for a queue. It is present exactly when `messages` is, lists each destination once and lists the destination of every `messages` entry; on an AMQP broker every entry is a queue. A fixture that breaks one of these rules fails its scenario. Before the input is sent, the replay subscribes to each topic and drains each queue, a JMS queue through a consumer it closes again at once, so the replay never takes a message the application consumes. After every other effect has matched, it compares each destination with its `messages` entries: a topic's and an AMQP queue's messages are received in order, each within `awaitMillis`, and no further one may arrive within 500 ms; a JMS queue is browsed, not consumed, until it holds exactly its entries within `awaitMillis`, and then every 100 ms until it has held exactly them throughout a 500 ms quiet window.
  - `tables`: the rows of every table the flow writes.
  - `collections`: the stored documents, without `_id`.
  - `mails`: `[{mimeBase64}]`, the mails the flow sent during the run, as raw MIME. The replay compares them with every mail GreenMail holds after the run, in any mailbox, except the input mail the replay delivered itself, which this comparison leaves out whether or not the flow removed it.
  - `mailboxes`: `{<email>: [{mimeBase64}]}`, the final contents of each named mailbox after the run, keyed by an email of `state.mail.users`: one raw MIME entry per message still in the mailbox, in mailbox order, the delivered input mail included when the flow did not remove it, and `[]` for a mailbox the capture found empty. The replay compares the message count first, then each message; a message flagged deleted but not expunged still counts.
  - `logs`: `[{logger, level, message}]`, every event the original's log shows, from the input to the end of the run, under each logger category an entry names, in logged order and whatever its level. The replay compares the events logged under those categories, and no others, with the entries one for one: the same number of events, each with its entry's `logger` and `level` and, in a `deterministic` scenario, exactly its `message` (an absent or null `message` reads as empty), so an extra, missing or reordered event fails the scenario. It waits up to `awaitMillis` for that stream to match, then compares it every 100 ms until it has matched throughout a 500 ms quiet window, so a further event arriving late fails too. `"logs": []` names no logger and constrains nothing.

Placeholders, allowed in `state.properties` values, in `request.file.directory` and in directory keys, and resolved at replay:

- `${wiremock.baseUrl}` (`http://localhost:<port>` of the WireMock server that serves `upstream`) and `${wiremock.port}`.
- `${dir:<name>}`: a temporary directory `<name>`, created on first use. A directory key or value without `${` is read as `${dir:<value>}`. Every directory key, `request.file.directory` and directory-spec `state.properties` value (one that begins with `${dir:`) must resolve inside the replay's temporary root; `..` traversal, an absolute path outside it or a symbolic link out of it fails the fixture. Each directory a key or `request.file.directory` resolves to is created when used and emptied after every scenario; a `state.properties` value is checked but not created, since it may name a file.
- `${freePort:<name>}`: a port the replay owns, the same one for every use of the same name and distinct from the port of every other name. The embedded servers bind a port themselves and publish it under their names, `amqp` (Qpid Broker-J), `ldap`, `greenmail.<proto>` and `mongo`, so `${freePort:amqp}` is the broker's AMQP port. Any other name, or one of these whose server's library the project lacks, gets a port the replay reserves until the class ends with an unconnected socket on the wildcard address. Until the application context starts its listeners, that socket is bound without `SO_REUSEADDR`, so no other process and no other name binds the port, with `SO_REUSEADDR` or without it, and a connection to it is refused. Just before the embedded web server binds its listeners, the replay swaps it for a socket bound with `SO_REUSEADDR` on the same port, so the application's listeners, which set `SO_REUSEADDR` as Undertow does, bind beside it. Only between this handover and the end of the context's refresh can another socket bind the port as well: one that sets `SO_REUSEADDR` throughout, and any socket in the instant each swap takes. Once the context has refreshed, a port nothing listens on is held without `SO_REUSEADDR` again, so it stays a refused connection and a listener that binds only later cannot bind it, and a port a listener bound is left to that listener, which keeps every other socket off it; a name first used after that is held without `SO_REUSEADDR` at once. A host whose sockets do not let such a listener bind beside a shared socket gets each reservation released, not shared, at the handover, with a warning, so another process can take a port until the application's listener has bound it; once the context has refreshed, each port nothing listens on is held without `SO_REUSEADDR` again, and the ports stay distinct there too.
- `${greenmail.<proto>.port}`, where `<proto>` is `smtp`, `smtps`, `imap`, `imaps`, `pop3` or `pop3s`: the port GreenMail's server for that protocol bound.
- `${mongo.uri}` and `${ldap.port}`: the address of the embedded MongoDB server and the port the embedded LDAP server bound.

Any other placeholder fails the class with a message naming the placeholder and the fixture.

## Comparison rules

- `deterministic`: status, reason, `Content-Type`, `Location` and body bytes are compared byte for byte, with no trimming or normalization; produced files and message bodies are compared the same way. The only substitution is the replay port inside `Location` (`:<request.port>` becomes `:<replay port>`).
- `scheduler` trigger, the trigger of this project: the upstream calls (every recorded exchange, in order), the rows of `contact` (`response.tables`: every captured column of every row, in the order the replay reads them, `SELECT * FROM contact ORDER BY 1`) and the log events of `response.logs` (the flow's `logger` elements of lines 51, 57 and 66, in logged order) are compared, under the rule of the row's state. The batch result and the stored watermark have no comparable field in this format; they are Tier 2A verification points read from the evidence of Capture step 5 (Project notes, Compared effects).
- `nondeterministic`: status, reason and the checked headers are compared exactly. Bodies, files and messages are compared for structure only: JSON by each object's member names in order, every occurrence of a repeated name kept, value kinds and array lengths; XML by child element names (namespace and local name) in order and attribute names as a set, with namespace declarations excluded and text ignored; any other body by empty versus non-empty. Produced files pair up by name: same-named files pair first, and every other name pairs with one of the same shape, which reads each canonical UUID (8-4-4-4-12 hexadecimal digits of either case joined by hyphens, not run together with another letter or digit) as `<uuid>` and then each remaining digit run as `#`, and keeps every other character, a literal `#` or `<` included, so prefixes, fixed segments and suffixes must match exactly, both sides must hold each shape equally often, and the names of one shape pair in sorted order; logs compare the same complete stream entry for entry, by logger and level and only by whether the message is empty; upstream request bodies are not matched. The scenario is reported `UNVERIFIED — nondeterministic output`.
- `unreachable`: no fixture may exist; the proof belongs in the row (AAP 0.8.2). A fixture for an unreachable row fails the class, and the scenario is `FAILED`.

Each run writes `target/fixture-parity/summary.properties` in the project directory: first the counts `verified=<n>`, `unverified=<n>` and `failed=<n>`, then one `scenario.<name>=<STATUS>` line per row, in row order. The statuses:

- `VERIFIED`: a captured deterministic fixture matched.
- `UNVERIFIED-nondeterministic`: a nondeterministic fixture matched in structure only.
- `UNVERIFIED-no-upstream`: the fixture has no `upstream` key.
- `UNVERIFIED-missing-driver`: the project has no replay driver (library, bean or port) for the row's trigger.
- `UNVERIFIED-uncaptured`: the row has no fixture file.
- `UNREACHABLE`: an unreachable row with no fixture.
- `FAILED`: a mismatch, a fixture for an unreachable row, or a fixture with no matching row.

`VERIFIED` counts as verified, every `UNVERIFIED-*` status as unverified and `FAILED` as failed; `UNREACHABLE` is counted in none.

With no fixtures the test is reported skipped (`Assumptions.assumeTrue`, reason `no Tier 2A fixtures captured`), never failed. For this project the summary then holds `verified=0`, `unverified=6` and `failed=0`, followed in table order by one `scenario.<name>=UNVERIFIED-uncaptured` line for each of `scheduler-poll-default-watermark`, `scheduler-poll-new-contact-inserted`, `scheduler-poll-existing-contact-updated`, `scheduler-poll-no-records`, `scheduler-poll-record-failure` and `scheduler-poll-upstream-unavailable`, and `scenario.scheduler-poll-otherwise-branch=UNREACHABLE`.

These statuses feed the parity label of the project README and of the root `SUMMARY.md` (AAP 0.8.7):

- `PARITY: UNVERIFIED — Mule runtime unavailable` until fixtures are captured.
- `PARITY: VERIFIED — Tier 2A fixtures` only when every scenario other than an `unreachable` one is `VERIFIED`.
- `PARITY: PARTIAL — Tier 2A fixtures: <v> verified, <u> unverified` when every captured deterministic scenario matches but some scenarios remain unverified.
- `PARITY: FAIL — Tier 2A fixtures` when any scenario is `FAILED`.

The fallback never reports PASS. The README lists the unverified scenarios by name, and a scenario marked `ACCEPTED — structural comparison` (AAP 0.8.8) still counts as unverified.

Whether the connection pool's `INITIALISE_ONE` login at deployment (line 5) lets the application deploy is a Tier 2A verification point; an application that does not deploy leaves the scenario uncaptured.
   - The original folder and its flow, the watermark's `default-expression` included, stay unedited.
4. The journal is cleared and the archive deployed; the poll the deployment starts is the scenario's poll. The capture waits for that poll to end in the runtime's application log `L`, counted from the lines the log held before the deployment, as the original IT waits for the job's termination (`helper.awaitJobTermination`, IT line 112), then undeploys the application at once by removing its anchor file, before the next poll 60 s after the first. `END` is the text of the log line that ends the row's poll, read from a trial deployment of the same row, never from this file: the batch engine's line that the poll's job instance finished, or for `scheduler-poll-upstream-unavailable` the last line of the failed poll's report; a row whose poll logs no such line, as an empty record set may, waits 8 s after the deployment instead. For `scheduler-poll-upstream-unavailable` the journal is not cleared, since WireMock is stopped:

   ```sh
   L=<the application's log file in the runtime>; N=$(wc -l < "$L")
   curl -sS -X DELETE "http://localhost:$W/__admin/requests"
   cp <the original's archive> "$MULE_HOME/apps/"
   timeout 600 sh -c 'until tail -n +'"$((N + 1))"' "$1" | grep -qF -e "$2"; do sleep 1; done' sh "$L" "$END"
   rm -f "$MULE_HOME/apps/$A-anchor.txt"
   sleep 5
   tail -n +"$((N + 1))" "$L" > "target/fixture-capture/$S-runtime.log"
   ```

   A capture in which a second poll began before the undeployment, seen as a second `query` in `calls.txt` or a second job instance in the runtime log, or in which the recorded `query` response of a row that created a test Contact holds any other Contact, is discarded and repeated from step 3.
5. Once the application is undeployed, the journal, the recorded `upstream`, is saved, the stored watermark is read back with the tool of step 3 into `watermark-after.txt` (`none` when the store holds no value under `timestamp`), the `contact` rows are read back into `tables-after.json`, and the log effects are copied unedited: `logs.txt`, the lines of `target/fixture-capture/$S-runtime.log` whose category is that of the flow's `logger` elements, which declare no `category` (in Mule 3.8 the logger processor's own class, `org.mule.api.processor.LoggerMessageProcessor`); `batch.txt`, the lines of the batch engine that name the poll's job instance; and `calls.txt`, one line per recorded call in call order naming its operation:

   ```sh
   curl -sS "http://localhost:$W/__admin/requests" > "target/fixture-capture/$S-journal.json"
   read_contact "$D/tables-after.json"
   grep -F 'org.mule.api.processor.LoggerMessageProcessor' "target/fixture-capture/$S-runtime.log" > "$D/logs.txt"
   JOB=<the job instance ID the batch engine logged for the poll>; grep -F -e "$JOB" "target/fixture-capture/$S-runtime.log" > "$D/batch.txt"
   jq -r '.requests | reverse[] | (.request.body // "") as $b
     | [$b | capture("<([A-Za-z0-9_]+:)?(?<op>login|queryMore|query)[\\s>]").op][0] // "other"' \
     "target/fixture-capture/$S-journal.json" > "$D/calls.txt"
   ```

   `calls.txt` must hold exactly one `query`, followed by the `queryMore` calls of the pages the original read, which confirms that one poll ran. A `login` appears or not depending on when the connector's pool logged in; that, the paging, and for `scheduler-poll-no-records` whether the batch engine ran a job instance at all, are recorded as the original produced them, whatever they are (Project notes, Verification points). Where no job instance ran, as in `scheduler-poll-upstream-unavailable`, there is no `JOB` to select by, and `: > "$D/batch.txt"` replaces the `JOB` line; with WireMock stopped there is no journal either, so `: > "$D/calls.txt"` replaces the journal and `jq` lines. The journal is not converted into `upstream`, because its `login` exchange carries the live credentials and the live `serverUrl` and every later exchange the live session ID (Project notes); it stays under `target/fixture-capture/`. Last, the scenario's test Contact is deleted through the client of step 3, as the original IT's teardown deletes its Contact (IT lines 91-103, through the test flow `deleteContactFromSalesforce`, `test-flows.xml:25-30`), and the `contact` table is emptied for the next scenario.
6. After the last scenario, recording stops: the runtime is stopped, WireMock is already stopped (step 2), and the database `company` is dropped. The sandbox user's password and security token are reset and its sessions revoked immediately afterwards (capture note under the table).
7. Write `fixtures/<scenario>.json` from `request`, `state` and `response`, every captured value as produced:
   - `request.invoke` is `{"type": "trigger.ContactPollScheduler", "method": "pollOnce"}`; there is no `request.file`, message or mail.

The sandbox state and the refused connection of step 3 are not part of `state`, since the replay reaches no live Salesforce.
   - `upstream` is left out (Project notes, `serverUrl` routing and Upstream unavailable), so the replay reports the scenario `UNVERIFIED-no-upstream`.
   - `response.tables` is the content of `tables-after.json`, and `response.logs` holds one entry per event of `logs.txt`, in logged order: `logger` the category, `level` the level and `message` the message text exactly as the log shows it after the layout's prefix. `response` holds nothing else; `batch.txt` and `watermark-after.txt` stay evidence (Project notes, Compared effects).

A match means the scenario gets no fixture and its evidence is not committed. Captured values, rows and log text are never adjusted afterwards, to match the Java output or for any other reason.

## Integrity rule

- A fixture is never edited to match the Java output. A mismatch is fixed in the Java code; for the scenarios of this project, that means SC-15 `client/SalesforcePartnerClient` for the upstream exchanges and their paging, `service/ContactToDatabaseBatchService` for the query, the two steps, the log lines and the watermark update, `mapper/ContactRowMapper` for the step 1 mapping, `client/ContactRepository` for the lookup, insert and update, SC-7 `service/BatchJobRunner` for the job run and its result, SC-8 `service/WatermarkStore` for the stored watermark, or `trigger/ContactPollScheduler` for the poll's failure handling. No expected value is written by hand, in this file or in a fixture (AAP 0.8.4).
- `DECISIONS.md` records the Tier 2A blocked state ("Mule EE licence and EE Maven repository credentials unconfirmed") and the escalation of AAP 0.8.8: once both are confirmed, a human is notified to begin capture and receives the list of scenarios left unverified.

## Project notes

- Driver: every fixture's `request.invoke` names the single-run method `{"type": "trigger.ContactPollScheduler", "method": "pollOnce"}`, which the ST-2 `scheduler` driver calls by reflection. `pollOnce()` runs one poll of `triggerFlow` through `service/ContactToDatabaseBatchService.synchronize()` and returns its `model/BatchJobResult`, which the driver does not read; a failed poll is rethrown unchanged, with the watermark left as it was. Under the reference driver contract an exception thrown by `pollOnce()` is the scenario's error outcome: the driver does not catch it, so the replay ends there and reports the scenario `FAILED` before any effect is compared. Replay never uses the scheduled `poll()`, which logs ERROR `Poll of triggerFlow failed: <failure>` with the failure's type identifiers, Salesforce fault code and upstream, never its message or stack trace, and never rethrows: the replay boundary removes the `@Scheduled` processor, and `poll.initial-delay` of 3600000 ms would hold the first scheduled poll back for an hour even where a schedule survived. The application runs with `spring.main.web-application-type: none`. Outside replay, `synchronize()` is `synchronized`, so a poll run on demand never overlaps a scheduled one, as the original's `processingStrategy="synchronous"` flow (line 60) never ran two polls at once.
- Replay context: every fixture's `state.properties` holds these eleven entries with the same values, because one application context serves every fixture and one key resolving to different values fails the class. They extend the reference's keys in this project only, and they use the reference's placeholders wherever a value depends on the replay environment:
  - `spring.datasource.url`: `jdbc:h2:mem:fixture-company;MODE=MySQL;DATABASE_TO_LOWER=TRUE;CASE_INSENSITIVE_IDENTIFIERS=TRUE;IGNORECASE=TRUE;DB_CLOSE_DELAY=-1`, an H2 in-memory database in MySQL mode with the options of `application-test.yml` under a fixed name (rule 1 above the table). The replay boundary reads an `h2` in-memory URL as an embedded database that names no network target, and its table rules accept it as a database the replay owns.
  - `spring.datasource.username`: `sa`; `spring.datasource.password`: empty; `spring.datasource.driver-class-name`: `org.h2.Driver`. These replace `${mysql.user}`, `${mysql.password}` and the MySQL driver of `application.yml`; the H2 `sa` user exists only inside the in-memory database.
  - `spring.sql.init.mode`: `always`; `spring.sql.init.schema-locations`: `classpath:contact.sql`. The unchanged `contact.sql` creates `contact` once, when the context starts; the replay then empties and reseeds it from `state.tables` before each scenario.
  - `mysql.host`: `localhost`; `mysql.port`: `${freePort:mysql}`. With `spring.datasource.url` replaced they reach no client, but the replay boundary checks every key whose last segment ends with `host` together with its sibling `port`, and it fails the class on the empty default of `mysql.host` and on port 3306, which no replay server owns.
  - `watermark.store-path`: `${dir:watermark}/watermark.properties`, the SC-8 store file of `service/WatermarkStore`, a UTF-8 `java.util.Properties` file keyed `timestamp` (`ContactToDatabaseBatchService.WATERMARK_KEY`) inside the replay's temporary directory `watermark`. It overrides surefire's `target/test-watermark/watermark.properties` (`pom.xml`), so no watermark another test left there is read, and since the replay empties that directory around every scenario, no row inherits the watermark an earlier row's poll stored; `scheduler-poll-default-watermark` seeds no file and polls from the empty store with the default watermark.
  - `sfdc.auth-endpoint`: `${wiremock.baseUrl}/services/Soap/u/65.0`, because the replay boundary fails the class on its default Salesforce login endpoint. It serves the recorded SOAP `login` and `query` exchanges, and any `queryMore` the original made, in recorded order; a Java client that pages differently is fixed in the Java code, never in the fixture. The credential keys `sfdc.username`, `sfdc.password` and `sfdc.securityToken` stay empty: the Java client logs in lazily on its first Salesforce call, and the replay makes none, since it skips a fixture without `upstream`.
  - `poll.initial-delay`: `3600000` (header rule 5).
