It is written for the requester and for the person who later runs Tier 2A fixture capture. Evidence is cited as `path:line` against this checkout; "AAP n.n" refers to the section of the Agent Action Plan that settled the point. Values produced later (Tier 2A captures, unverified-scenario lists, Tier 2B results) are shown in their current state.

**Rules:** no user rules were provided for this project (`review_rules` returns "No user rules provided."; AAP 0.9), so none governs the conversion or this file.

Probe: setting the reason on the Undertow exchange from an `@ExceptionHandler` produced the raw status line `HTTP/1.1 400 Invalid input data`. In `proxying-a-soap-api-java` the guard's delegate worker keeps exactly the options of the worker Undertow would create, because that listener has no idle policy of its own. In each project `ListenerRequestParsingTest`, `ListenerHeaderWhitespaceTest`, `RequestFramingValidatorTest`, `RequestFramingConduitTest` and `ForwardedRequestHeadersTest` pin it |

## 4. Shared-component register

Projects share no runtime or build artefact. A behaviour that more than one project must carry out identically is implemented once, in its reference project, and copied into every other consumer with only the `package` line changed; its unit tests are copied the same way. Each component's dependencies are closed within its own row, so copying a row never needs a type the consumer lacks. A change to a shared component is made in the reference implementation and then copied to every consumer; a consumer never writes its own variant (AAP 0.4.4).

The reference implementation is the first consumer AAP 0.4.4 lists for the row; where a row names a group, it is the first member, in the folder order of AAP 0.2.1, that uses the class, which keeps the copy order acyclic. Paths are relative to `src/main/java/com/mulesoft/examples/<package>/` unless they start with `src/`; tests are relative to `src/test/java/com/mulesoft/examples/<package>/`. Project names omit the `-java` suffix.

## 6. Behaviour and contract decisions

### 6.1 `rest-api-with-apikit` 409

The RAML declares 409 for POST `/teams` (`rest-api-with-apikit/src/main/resources/leagues.raml:43`) and for PUT `/fixture/{homeTeamId}/{awayTeamId}` (`leagues.raml:156`), and the README describes a 409 exception strategy (`rest-api-with-apikit/README.md:56`), while the flow maps only the five APIkit codes (`rest-api-with-apikit/src/main/app/rest-api-with-apikit.xml:18-44`). The RAML contract governs: the ported `ConflictException` ("There is already a team with id <id>", "The match between team <h> and team <a> has not been played yet") is answered by `exception/LeagueExceptionHandler` with 409 and `{ "message": "<exception message>" }`. The 409 body is a plan default and a Tier 2A verification point. `RAML-CONTROLLER-DIFF.md` shows it as a RAML-governed row.

### 6.2 Salesforce authentication

- Six originals log in through the SOAP Partner API with username, password and security token (for example `import-contacts-into-salesforce/src/main/app/contacts-to-SFDC.xml:4`). SC-15 keeps that protocol: SOAP `login` through `PartnerConnection`/`ConnectorConfig` with `sfdc.username`, `sfdc.password` and `sfdc.securityToken`.
- SOAP `login` is not the OAuth 2.0 password grant. It was chosen because the request requires each conversion to match its original's mechanism and authorizes reusing the existing Salesforce credentials, and SOAP `login` needs nothing beyond them.
- The request forbids only new sandbox or tenant procurement, so an OAuth flow is not prohibited. It would need configuration this phase does not assume: a connected app registered in the existing tenant, whose consumer key and secret (password grant) or uploaded certificate and consumer key (JWT bearer) the requester would supply, plus a token exchange in SC-15. No such flow is built.
- `authenticating-salesforce-using-oauth2` keeps its original OAuth 2.0 authorization-code flow (`sfdc.key`, `sfdc.secret`) and uses SC-15 in session mode (session ID + instance URL from the issued token); the token refresh is its re-authentication step.

### 6.4 Approved connector failure modes

| Failure | Behaviour | Caller-facing result (HTTP-triggered projects) |
|---|---|---|
| Authentication or token expiry | Re-authenticate, then retry the call once; an authentication failure of the re-authentication or the retry ends the attempt | 502 `{ "message": "<upstream message>", "upstream": "<system>" }` |
| Rate limit / throttling | No retry | 429 with the vendor's `Retry-After` when present, same body |
| Timeout or connectivity failure (`SocketTimeoutException`, `HttpTimeoutException`, Netty `ReadTimeoutException`, `ConnectException`, `UnknownHostException`, `NoRouteToHostException`, other `SocketException`, anywhere in the cause chain) | Never retried | 503, same body |
| Anything else | Rethrown unchanged to the example's original exception branch | Original behaviour |

- `upstream` values: `Salesforce`, `NetSuite`, `Workday`, `Microsoft Dynamics 365`. Connect and read timeouts are 10 s for every vendor (the Mule default response timeout).
- Vendor classification: Salesforce `INVALID_SESSION_ID` → authentication, `REQUEST_LIMIT_EXCEEDED` → rate limit; NetSuite and Dynamics HTTP 401 → authentication (token cache evicted before the retry), 429 → rate limit; Workday HTTP 401 or SOAP fault `wsse:FailedAuthentication` / `wsse:InvalidSecurity` → authentication, 429 → rate limit.
- Retrying after an authentication rejection is safe for writes because the vendor refused the request before processing it; timeouts and connectivity failures are never retried, which protects every write (`sfdc:create` of Contact, Lead and Account, Workday `Put_Customer`, Dynamics contact create, the NetSuite customer create of the live tests).
- `UpstreamExceptionHandler` runs at the highest `@Order` in the five HTTP-triggered connector projects, so in `salesforce-data-retrieval` the three additions take precedence over the catch-all `Invalid Salesforce query.`, which still handles every other exception.
- File- and poll-triggered connector projects have no caller to answer: the classification is logged at ERROR with the upstream name, and batch jobs record the record as failed.
- No other new behaviour is planned in any project (AAP 0.4.8): no project carries another connector failure-mode addition, and the differences for hostile input are recorded in section 8, as is the response header hardening (the cache and content-sniffing headers on the six replies that carry customer, opportunity, employee or directory records).

### 6.6 JMS redelivery timing (`jms-message-rollback-and-redelivery`)

The original ActiveMQ `RedeliveryPolicy` is `initialRedeliveryDelay` 5000 ms, `redeliveryDelay` 2000 ms, `maximumRedeliveries` 5, no back-off (`jms-message-rollback-and-redelivery/src/main/app/jms-redelivery.xml:5-11`). ### 6.10 Cache store bound (`cache-scope-with-fibonacci`)

The original's `ee:object-store-caching-strategy` declares no object store (`cache-scope-with-fibonacci/src/main/app/cache-scope.xml:35`), and the limits of the store Mule 3.8 then uses are not documented (Documentation, below). The converted cache takes the Mule 3.8.0 core in-memory store defaults (`github.com/mulesoft/mule`, tag `mule-3.8.0`, `core/src/main/java/org/mule/util/store/`), which are also the documentation's configuration for a per-node in-memory cache:

| Limit | Mule 3.8.0 in-memory store default (source) | Converted (`application.yml`) |
|---|---|---|
| Entry count | `maxEntries` 4000 (`AbstractMonitoredObjectStore.java:41`) | `spring.cache.caffeine.spec: maximumSize=4000` |
| Time to live | `entryTTL` -1, so no entry expires (`AbstractMonitoredObjectStore.java:47`); `expire()` applies a TTL only when `entryTTL` > 0 (`InMemoryObjectStore.java:151-152`) | No expiry or refresh set |
| Enforcement | `expire()` runs every `expirationInterval` 1000 ms (`AbstractMonitoredObjectStore.java:55,79`) and first trims the store to `maxEntries`, removing the oldest-inserted entries (`InMemoryObjectStore.java:143-149`) | Caffeine evicts during its own cache maintenance, by its frequency-and-recency policy |

- Reason: the key is the raw `n` string, exactly as the original key expression yields it (AAP 0.3.2), so every caller-chosen spelling of `n` (`007`, `7`, `7.0`, `1.<digits>`) is a separate entry, as in the original. Without a bound those keys would grow the heap without limit.
- Difference: past 4000 distinct keys the in-memory store drops the oldest-inserted entries once a second, while Caffeine evicts by its own policy, so which keys survive, and so which later requests answer `COST: 0`, can differ. This is a Tier 2A verification point.
- Documentation: the Mule 3.8 cache-scope page (`archive.docs.mulesoft.com/mule-runtime/3.8/cache-scope`) does not settle the original's store. Its "Object Stores and Clustering" section states that since Mule 3.5.0 a new caching strategy without an object store uses an object store instance that provides a unified cache for all cluster nodes, that only the cache scope's default caching strategy uses `InMemoryObjectStore` (the original's scope references its own `Caching_Strategy`, `cache-scope.xml:63`), and that a cache per cluster node needs a managed store over an in-memory store with `maxEntries` 4000, `entryTTL` -1 and `expirationInterval` 1000. Its caching-strategy field table, by contrast, says Mule stores cached responses in an `InMemoryObjectStore` by default. The page does not state the limits of the store a strategy without one uses in a standalone runtime, and the EE source is not public, so whether the original bounded its cache at 4000 is a Tier 2A verification point. A captured fixture governs: a capture showing another limit, or none, changes the spec to match.
- Tests: `controller/FibonacciControllerTest` asserts the 4000-entry maximum, the absence of expiry and refresh, and that 5000 distinct keys leave 4000 entries.

## 8. Query hardening

Several originals build queries by concatenating request input. The conversion returns the same rows for every legitimate input while closing injection, which is the plan's only intentional difference for hostile input (AAP 0.4.10). The script evaluation paragraph records the difference that follows from running no script engine (AAP 0.3.2), the email filter evaluation paragraph the one that follows from evaluating the email pattern in linear time, the OAuth callback state paragraph the difference for hostile input that the security review of the `authenticating-salesforce-using-oauth2` callback required, recorded here beside query hardening, the response header hardening paragraph the cache and content-sniffing headers added to the replies that carry customer, opportunity, employee or directory records, the browser script restriction paragraph the script policy header `websphere-mq-java` adds to its copied page as partial hardening against stored script injection, a difference for hostile input only, and the implementation safety controls and the log output escaping listed at the end of this section are decisions taken in the code, not plan decisions. Queries are hardened as follows:

- SQL values are bound as parameters.
- Values inside SOQL string literals are escaped: backslash → `\\`, single quote → `\'` (`SalesforceRetrievalService.escapeLiteral` in `salesforce-data-retrieval-java`).
- Values inside SuiteQL string literals are escaped by doubling each single quote (`O'Brien` → `O''Brien`, SC-16 `NetsuiteRestClient.suiteQlLiteral`). SuiteQL follows Oracle literal rules, under which a backslash is an ordinary character that cannot end the literal, so it is left unchanged; escaping it would change the value matched for legitimate input.
- In `salesforce-data-retrieval`, the caller-supplied SOQL object, search key and field list are checked against `describeGlobal`/`describeSObject` (relationship paths resolved hop by hop, names compared case-insensitively as SOQL compares them). A non-matching identifier fails before Salesforce is queried and is answered with the original `Invalid Salesforce query.`.

OAuth callback state: in `authenticating-salesforce-using-oauth2`, the original flow sets no `state` on `sfdc:authorize` (`authenticating-salesforce-using-oauth2/src/main/app/salesforce-oauth.xml:12`), and whether the Mule 3 DevKit connector generated or validated one of its own is not established (the DevKit 3.8 OAuth 2.0 documentation does not settle its default), so no claim is made that the original lacked such protection. Without a check, a callback carrying a valid code that an attacker obtained under their own Salesforce identity, opened in a browser that never started an authorization, would be exchanged and would replace the application's one shared grant (CWE-352). `service/SalesforceOAuthService` in `authenticating-salesforce-using-oauth2-java` therefore binds each authorization it starts to the browser: every `/` redirect issued while no token is held carries a fresh `state` (32 `SecureRandom` bytes, base64url without padding) as the last `Location` parameter, and sets the same value in the cookie `sfdc_oauth_state` (`HttpOnly`, `SameSite=Lax`, `Path` the callback path, `Max-Age` the new non-secret key `sfdc.oauth.state-ttl`, default `10m`, `Secure` only for an `https` `redirect_uri`). A callback with a code is refused before any token request, with SC-1's 500 `{ "message": "Salesforce authorization failed: <reason>" }`, when its `state` or cookie is missing (`no state parameter`, `no state cookie`), when they differ (`state does not match this browser's authorization request`, compared in constant time), when the state names no pending authorization (`unknown or already used state`: never issued, already completed, or forgotten) or when it has expired (`authorization request expired`); the matching pending authorization is consumed by its first check, so each state completes at most once. A legitimate login started at `/` is answered with the same bytes as before; only the redirect's `state` parameter and its cookie are new. The grant stays the application's one shared grant: no login, session or per-user authorization is added (AAP 0.4.1). ### Verification points reported during conversion

Beyond the plan defaults of section 6.5, the conversion recorded these platform-level behaviours for comparison against the captured originals; the captured fixture governs each:

- SOAP listeners (SC-11): SAAJ's SOAP 1.1 message factory answers an envelope posted with a `Content-Type` other than `text/xml` (or none) with HTTP 500 and a `soap:Client` fault ("Invalid Content-Type…" or "Cannot create message: incorrect content-type for SOAP version…"), where CXF is believed to have accepted it.
- SOAP listeners (SC-11): SAAJ keeps the request headers `Accept` and `SOAPAction: ""` in every message's MIME headers, which Spring WS copies onto the response; `SoapListenerBoundaryAdapter` drops both, so SOAP responses and faults carry neither, as CXF sent neither. SAAJ's serializer writes characters outside the Basic Multilingual Plane as numeric character references (`&#128512;`); the messages of `SoapEnvelopeStyleInterceptor.CxfStyleMessageFactory`, the message factory of every SC-11 consumer, write them as raw UTF-8, as CXF wrote them, in responses, faults and outbound SOAP requests alike, with `Content-Length` counting those bytes. Both remain comparison points against the captured originals.
- SOAP listeners (SC-11): in the five projects that carry `config/SoapFaultConfig`, a valid SOAP 1.1 envelope whose body root no endpoint maps reaches its `UnknownOperationEndpointMapping`, which is consulted after every other endpoint mapping (order `LOWEST_PRECEDENCE`) and whose endpoint throws `UnknownOperationException`. `CxfStyleSoapFaultResolver` answers it with HTTP 500 and a SOAP 1.1 `soap:Client` fault in the envelope form of `SoapEnvelopeStyleInterceptor`. The `faultstring` is CXF's text, `Message part {<namespace>}<localName> was not recognized.  (Does it exist in service WSDL?)`, with two spaces before the parenthesis; for an empty Body it is `Message part null was not recognized.  (Does it exist in service WSDL?)`. The resolver logs one WARN line naming only the fault kind, the exception type and its throw site. In `soap-webservice-security`, `WebServiceConfig.SecurityFirstMessageDispatcher` enforces the path's WS-Security policy before any endpoint mapping runs: on the five secured paths an envelope without the required `wsse:Security` header gets the `wsse:InvalidSecurity` fault whatever its body root, and only an envelope that passes the policy, or any envelope on `/services/unsecure`, reaches the unknown-part fault. Whether the originals' CXF stack sent the same bytes and `faultstring` for an unknown wrapper and for an empty Body is unverified.
- SOAP listeners (SC-11): in the four projects whose originals expose `cxf:jaxws-service`s (`foreach-processing-and-choice-routing`, `legacy-modernization`, `service-orchestration-and-choice-routing`, `soap-webservice-security`), a SOAP 1.1 request carrying a `mustUnderstand="1"` header block addressed to the receiver (no actor, or the `next` actor) that no interceptor of the mapped endpoint understands is answered before any endpoint runs by `CxfStyleSoapMessageDispatcher` in its checked mode, each project's `messageReceiver` bean (extended by `WebServiceConfig.SecurityFirstMessageDispatcher` in `soap-webservice-security`): HTTP 500, `soap:MustUnderstand`, `faultstring` `MustUnderstand headers: [{<namespace>}<localName>] are not understood.`, no `faultactor`. The text is the `MUST_UNDERSTAND` key of CXF 2.7's `Messages.properties`, `MustUnderstand headers: {0} are not understood.`, whose `{0}` CXF filled with a `HashSet<QName>`, so the names are rendered by `HashSet.toString`: a repeated block once, several blocks in hash order, which Java 8 and Java 17 compute alike, and an unqualified block as its local name. Spring WS's own text, `One or more mandatory SOAP header blocks not understood`, is not used. The dispatcher logs one WARN line carrying only the number of blocks. `xml-only-soap-webservice` follows its originals' three `cxf:proxy-service` listeners instead: its `messageReceiver` is the dispatcher's unchecked mode, which examines no header block, so such a request is processed as any other. Mule 3.8's `ProxyServiceMessageProcessorBuilder.configureServer` removes CXF's `MustUnderstandInterceptor` from the binding's inbound interceptors of every proxy service, whatever its payload mode, so those originals answered no MustUnderstand fault. The fault text is derived from CXF's source, not captured; whether the four `cxf:jaxws-service` originals sent these bytes is unverified.
- SOAP listeners (SC-11): in the five projects that carry `config/SoapFaultConfig`, a `NullPointerException` the JVM raised inside an endpoint (exactly that type, with a message in the JDK's computed form `Cannot <action>`, optionally followed by ` because <what> is null`) is answered as an exception without a message: `soap:Server` with CXF's `Fault occurred while processing.`. The originals ran on Java 8, which gave such exceptions no message; Java 14 and later compute one naming internal classes, methods and variables, for example for a `foreach-processing-and-choice-routing` `getLoanQuote` whose `arg0` carries no `creditProfile`. An exception given a message by its own code keeps it. Other exception messages that changed between Java 8 and Java 17, such as those of `ArrayIndexOutOfBoundsException` or `ClassCastException`, are passed through unchanged.
- HTTP listeners, CORS pre-flights: the 37 projects that carry `config/PreflightDispatchConfig` look a pre-flight to which no CORS configuration applies up as the plain `OPTIONS` request it is, so it gets what any `OPTIONS` request to that path gets: the flow's response, the listener's 405 or the no-listener 404.
